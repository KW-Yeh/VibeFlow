# Spec：盤點與自主放行

- 狀態：已確認
- Ticket：尚無
- 需求來源：使用者需求（2026-11-25，對話中逐步定案）。卡片先經過「盤點」，用 headless 方式產出 spec.md、plan.md 與執行準備，並把需要使用者準備的資源（例如 JFrog auth token）盤點清楚。之後由一個放行開關依序放行準備好的卡片；卡片碰到額度上限時自己等待重置並接續原 session；關閉開關時產生這一批的報告，存放在 VibeFlow 內。
- 更新日期：2026-11-25（同日追加盤點放寬權限）
- 確認紀錄：2026-11-25 使用者看過完整 spec 與六個待確認事項後回覆「都照預設」，六項依建議定案（見「已定案決策」最後六條）。
- 後續變更：2026-11-26 起，盤點欄、盤點 pass 與「盤點中」「待回答」兩個狀態已移除；放行開關改為「下班派工」，批次會自動結束並產生晨報。本文件的盤點與放行部分只作為決策紀錄，現行行為見 [night-shift](../night-shift/spec.md)。

## 問題與目標

目前一張卡從 Backlog 拖進 In Progress 後，agent 才開始讀需求。這時才發現缺少授權、檔案或 token（例如新增套件要走 `install-library`，需要 JFrog auth token），卡片就停下來等人。使用者必須守在旁邊，一張一張回答、一張一張啟動。額度用完時，卡片也只會停住，要等使用者回來手動喚醒。

目標：

1. 執行前先「盤點」。卡片在 headless 模式產出 spec.md、plan.md，以及 plan.md 內的「執行準備」段落，把所有需要使用者決定或準備的事一次列出並實際驗證。全部就緒後，卡片被標為「準備開工」。
2. 使用者打開「放行」開關後，VibeFlow 依序放行準備開工的卡片，受並行上限限制。卡片用全新的 agent session，照 spec 與 plan 實作、驗收、修正、開 PR。
3. 卡片碰到額度上限時，等到重置時間，對原 session 送出「繼續」，不需要人介入。
4. 卡片的狀態用保留的狀態標籤表示，人在看板上一眼就看得懂，程式也能用同一份資料判斷。
5. 關閉放行開關時，VibeFlow 依這一批被放行卡片的結果產生報告，存放在 VibeFlow 內。只有產生報告這一步需要 agent。

## 已定案決策

以下是 2026-11-25 對話中使用者已選定的方向，寫在這裡作為 spec 的前提：

- 不設「資源控管者」agent。放行與排程由 VibeFlow 程式執行；只有產生報告時才呼叫 agent。
- 不做用量預估。額度不足的處理方式是「事後偵測額度上限，等待重置」。
- 盤點用 headless 方式執行，沒有終端機，沿用卡片上的設定（agent、model、effort、專案、base 與分支、附件）。盤點時就建立 worktree 與分支。
- 盤點需要使用者補充時，使用者在任務詳情頁的盤點區用貼上或附加檔案的方式提供額外 context。
- 放行開關開著時，放行所有帶「準備開工」標籤的卡片，包含開關開啟後才盤點完成的卡片。
- 關閉開關只停止放行新卡片，已在執行的卡片繼續跑完。
- 額度已用完、無法用 agent 產生報告時，程式先產生表格版報告，額度恢復後再由 agent 補上敘述。
- 報告預設保留 10 份，數量可以調整。
- 卡片碰到額度上限後，沿用原 session 接續。
- 狀態用卡片標籤表示，透過 CLI 寫入。
- 盤點區、設定頁、報告頁的視覺設計之後交給 Design 處理；本 spec 只定義需要哪些元素與行為。
- 狀態標籤清單為：盤點中、待回答、準備開工、執行中、等待額度、待你確認、卡住、已開 PR。
- 並行上限計算 In Progress 欄中所有正在執行的卡片，包含手動拖入的，不含 master 卡。
- heartbeat 自動接續所有 In Progress 卡片，不限於放行批次內的卡片。
- TUI 只顯示盤點欄與狀態標籤，不提供盤點操作與報告檢視。
- 設定預設值：並行上限 2、heartbeat 間隔 5 分鐘、報告用 Claude 低成本 model 與 low effort。
- 盤點欄的卡片不能直接編輯描述，補充內容一律透過盤點區的額外 context。
- 2026-11-25 追加：盤點放寬權限，讓 agent 能用各種 MCP 與 skill 找出最佳做法。使用者回覆「照預設做」，採以下四項：Claude 盤點改用 auto mode（保留 secret 路徑禁讀）；外部系統只讀，需要寫入時列進待決定事項；可以在 worktree 試做，結束前自行還原，VibeFlow 檢查到殘留就標「待回答」、不自動刪除；Codex 維持 workspace-write sandbox 加網路，另外透過 `CODEX_HOME` 拿到 Library skills。

## 範圍

### 本次包含

- 看板新增「盤點」欄，位於 Backlog 與 In Progress 之間，以及相關的拖曳規則。
- 盤點流程：headless 執行、建立 worktree 與分支、產出 spec.md 與 plan.md（含「執行準備」）、驗證資源、重新盤點。
- 任務詳情頁的盤點區：顯示盤點結果、待回答的問題與缺少的資源，並讓使用者貼上或附加額外 context。
- 保留的狀態標籤，以及設定狀態的 CLI 指令。
- 額度上限偵測，以及每張 In Progress 卡片各自的 heartbeat：等待重置、探測、對原 session 送出「繼續」。
- 放行開關與放行批次：依序放行、並行上限、記錄批次內的卡片與狀態事件。
- 批次報告：關閉開關時產生、表格版備援、agent 補寫、在 VibeFlow 內檢視、保留份數。
- 設定：並行上限、heartbeat 間隔、報告保留份數、報告使用的 agent、model 與 effort。
- `vibeflow-state.json` 新形狀的 migration。

### 本次不包含

- 用量預估、依剩餘額度排序或挑選卡片。
- 獨立的「資源控管者」agent。
- 固定時間（例如每天 9:00）產生報告。
- host 沒有在執行、或電腦睡眠時的排程。heartbeat 只在 VibeFlow host 執行時運作。
- master 卡片進入盤點或被放行。master 卡維持現有行為。
- 盤點區、設定頁、報告頁的視覺設計。
- TUI 的盤點操作與報告檢視。TUI 只顯示盤點欄與狀態標籤。
- 直接編輯盤點欄卡片的描述。

## 行為

### 盤點

| 情境或觸發條件 | 預期行為 |
| --- | --- |
| 使用者把 Backlog 卡片拖進「盤點」，或從 CLI 對卡片開始盤點 | 卡片移到盤點欄，掛上「盤點中」標籤。VibeFlow 依卡片設定建立 worktree 與分支，沿用 `ensureProvisioned` 的規則。接著用 headless 方式啟動 agent，任務是產出 spec.md、plan.md 與「執行準備」，不做功能實作。盤點沒有終端機。 |
| 盤點用的 agent 權限 | Claude 以 auto mode 執行：MCP、skill（含 VibeFlow Library）、網路、subagent 都可以用，高風險動作由 auto mode 的分類器擋下；設定中的驗證指令不經審核直接放行；secret 路徑一律禁讀。Codex 在 workspace-write sandbox 加網路中執行，透過 `CODEX_HOME` 取得 Library skills。外部系統只讀：送單、改 ticket 狀態、發訊息這類寫入不做，改列為待決定事項。 |
| 盤點時試做程式碼 | 為了比較做法，agent 可以在 worktree 中修改程式碼、執行實驗，但結束前必須還原，只留下功能文件目錄的變更。盤點結束後，VibeFlow 檢查 worktree：功能文件目錄以外仍有變更時，卡片掛「待回答」，原因列出殘留的檔案；VibeFlow 不自動刪除或還原。 |
| 盤點產出的「執行準備」 | 列出四類內容：需要使用者決定的事項、執行階段會用到的指令與權限、需要的資源（檔案、帳號、token、測試資料）與驗證結果、允許的遠端操作（commit、push 到卡片分支、開 draft PR 等）。另外列出停止條件。 |
| 驗證需要 secret 的資源（例如 JFrog auth token） | agent 不讀取、不輸出、不記錄 secret 的值，只執行會用到認證、但不會印出值的檢查，記錄「通過或失敗」。 |
| 盤點完成，所有項目都已就緒 | 卡片標籤換成「準備開工」，仍留在盤點欄。plan.md 標為可以直接執行。 |
| 盤點完成，但有待決定的事項或缺少的資源 | 卡片標籤換成「待回答」。盤點區列出每個問題與缺少的資源。 |
| 使用者在盤點區貼上文字或附加檔案，然後重新盤點 | 新增的內容存成卡片的額外 context，不改動卡片原本的描述。VibeFlow 再跑一次 headless 盤點，以既有的 spec.md、plan.md 與新的 context 為輸入，更新文件並重新驗證。 |
| 盤點中的 headless 程序因額度上限結束 | 卡片掛上「等待額度」，heartbeat 在重置後重新啟動盤點。 |
| 盤點中的卡片被拖回 Backlog | 盤點程序停止。worktree 與分支依 Backlog 卡片的現有規則處理：乾淨的就收掉，有變更的拒絕移動。 |
| 帶「準備開工」的卡片被使用者直接拖進 In Progress | 和被放行一樣啟動執行。手動拖曳仍然可用。 |

### 執行

| 情境或觸發條件 | 預期行為 |
| --- | --- |
| 盤點完成的卡片進入 In Progress（被放行或手動拖入） | 用全新的 agent session 啟動，在盤點建立的同一個 worktree 與分支上工作。第一則訊息指向該卡的 spec.md 與 plan.md，並說明授權範圍以「執行準備」為準。卡片標籤換成「執行中」。 |
| 執行中碰到停止條件，或需要「執行準備」以外的授權 | agent 透過 CLI 把卡片狀態設為「待你確認」或「卡住」並附上原因，然後停止。 |
| 執行完成並開出 PR | agent 把卡片狀態設為「已開 PR」。 |

### 狀態標籤

| 情境或觸發條件 | 預期行為 |
| --- | --- |
| VibeFlow 啟動 | 確保保留的狀態標籤存在：盤點中、待回答、準備開工、執行中、等待額度、待你確認、卡住、已開 PR。程式用固定的 id 辨認，使用者改名或改色不影響判斷。 |
| agent 或使用者執行 `task status --set <狀態> [--reason <文字>]` | 移除卡片上其他的狀態標籤，掛上指定的那一個，記錄原因與時間。一張卡同時最多只有一個狀態標籤。 |
| 指定的狀態不在保留清單內 | 指令失敗並列出可用的狀態。不會建立新標籤。 |
| 使用者手動移除或加上狀態標籤 | 視為使用者覆寫，同樣記錄成一筆狀態事件。 |
| 一般標籤（非狀態標籤） | 行為不變，可以和狀態標籤並存。 |
| 卡片進入 Done | 依現有規則清掉所有標籤。狀態歷史保留在放行批次的事件紀錄中，報告不受影響。 |

### 額度上限與 heartbeat

| 情境或觸發條件 | 預期行為 |
| --- | --- |
| 任一 In Progress 卡片或盤點程序碰到額度上限 | VibeFlow 從 agent 的 transcript 或輸出判斷出額度上限，把重置時間存在卡片上（不放進標籤名稱），卡片掛上「等待額度」。 |
| 重置時間到（加上一段緩衝） | heartbeat 對該卡的 provider 送出一個最小的探測請求。通過後，經由 `mailbox.ts` 對原 session 送出「繼續」；原程序已經結束的就 resume 原 session。狀態標籤恢復成進入「等待額度」前的狀態。 |
| 探測仍然失敗，或判斷不出重置時間 | 依設定的 heartbeat 間隔反覆探測，直到通過。 |
| 卡片在等使用者回答、卡在權限對話框，或使用者正在輸入 | heartbeat 不送任何訊息。 |
| 多張卡片使用不同的 provider | 每張卡依自己的 provider 與重置時間各自等待、各自接續，互不等待。 |
| host 重新啟動 | 依卡片上存的重置時間重建計時器。 |

### 放行開關與批次

| 情境或觸發條件 | 預期行為 |
| --- | --- |
| 使用者打開放行開關 | 建立一個新的放行批次，記錄開始時間。依盤點欄的卡片順序，放行帶「準備開工」的卡片到 In Progress，直到達到並行上限。 |
| 開關開著，有卡片離開執行（進入 Done，或狀態變成「待你確認」「卡住」「已開 PR」） | 名額空出，放行下一張準備開工的卡片。 |
| 開關開著，有新的卡片盤點完成 | 依盤點欄順序排入，有空的名額就放行。 |
| 卡片處於「等待額度」 | 仍然佔用並行名額。 |
| 計算並行上限 | 計算 In Progress 欄中所有正在執行的卡片，包含手動拖入的，不含 master 卡。 |
| 每張被放行的卡片 | 記錄到這個批次。卡片之後每次狀態改變，都寫一筆事件（時間、卡片、狀態、原因）。 |
| 使用者關閉放行開關 | 不再放行新卡片。已在執行的卡片繼續跑完。批次記錄結束時間，開始產生報告。 |
| 開關開著時 host 重新啟動 | 開關狀態與批次保留，host 啟動後繼續放行。 |

### 報告

| 情境或觸發條件 | 預期行為 |
| --- | --- |
| 放行開關關閉 | VibeFlow 先產生表格版報告，內容只有事實：批次內每張卡的最後狀態、原因、token 用量、耗時、PR 連結、狀態時間軸。接著用設定的 agent、model 與 effort 補上敘述：完成了什麼、卡在哪個環節、哪些卡片比其他卡片更花時間或額度。 |
| 產生報告時額度已用完 | 保留表格版，報告標為「待補寫」。額度恢復後由 agent 補寫。 |
| 關閉時還沒跑完的卡片 | 報告標為「進行中」。下一個批次不會重複追蹤這些卡片。 |
| 使用者在 VibeFlow 內開啟報告 | 依時間列出報告，可以開啟任何一份閱讀。 |
| 報告份數超過保留上限 | 刪除最舊的報告。調低上限時，多出來的舊報告在下一次寫入報告時刪除。 |

### 設定

| 設定項目 | 預設 |
| --- | --- |
| 並行上限 | 2 |
| heartbeat 探測間隔 | 5 分鐘 |
| 報告保留份數 | 10 |
| 報告使用的 agent、model、effort | Claude、低成本 model、low |

## 限制與依賴

- **額度上限的訊號是未驗證的前提。** Claude Code 與 Codex 碰到額度上限時，transcript 或輸出會留下什麼、有沒有附上重置時間，都還沒有實測。這些格式不是公開 API。plan 的第一階段必須先實測並用 fixture 固定格式；判斷不出重置時間時，退回依間隔反覆探測。
- headless 盤點不能使用 `AskUserQuestion` 這類互動工具。所有問題都必須寫進「執行準備」與盤點區。
- 盤點的權限：Claude 使用 auto mode（`--permission-mode auto`）加上 secret 路徑的 `--disallowedTools`；auto mode 是否可用取決於帳號與 model，和執行階段開 Auto Mode 時相同。Codex 使用 workspace-write sandbox；`codex exec` 中 MCP 工具是否可用依 Codex 自己的設定。
- 送訊息給 agent 一律經過 `mailbox.ts`，遵守它對草稿、權限對話框與使用者輸入的保護。
- `writeBoard` 會清掉 Done 卡片的標籤。報告的資料來源是批次的事件紀錄，不是標籤。
- 看板新增欄位、放行批次、報告索引、卡片上的重置時間與額外 context 都會改變 `vibeflow-state.json` 的形狀，需要調整 `version` 並寫 migration。報告內文存成獨立檔案，state 只存索引。
- heartbeat 只在 VibeFlow host 執行時運作。電腦睡眠或 host 關閉期間不會接續任何卡片。
- 執行階段沿用使用者既有的 `work-mode`、`feature-spec-plan`、`pr` skill。「執行準備」中的授權屬於 `feature-spec-plan` 所說的「既存明確授權」。
