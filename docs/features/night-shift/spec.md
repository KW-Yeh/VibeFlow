## 問題與目標

[autonomous-run](../autonomous-run/spec.md) 的設計是持續排隊、逐步消化，跟實際的工作節奏對不上：

- **盤點是每張卡各跑一輪 headless pass。** 有問題要等 pass 結束、補 context、再跑一輪，人不能直接和 AI 對話。盤點也不會拆卡或合卡，但白天最需要的就是把 Feature 拆小、把同元件的 eBug 合併。白天的整理應該是人和 agent（或 master 卡）直接對話。
- **放行是一個開關。** 要記得打開，也要記得關掉，關掉才產生報告。實際需要的只是「下班時按一次」。
- **agent 結束回合但沒有回報時，卡片會一直佔著名額。** 晚上沒人守著，這張卡會卡住整個批次，報告永遠出不來。
- **方向錯的卡沒有「改單、當晚重派」的路徑。**
- **work-mode 會在夜裡卡住。** work-mode 已經依任務類型（bug fix、feature、refactor…）選 playbook，但它會停下來等 spec／plan 確認，開 PR 後還會一直盯到 merge。夜裡沒人確認，卡片會停到天亮，或永遠不結束。

目標：

1. 看板只有待辦、進行中、已完成三欄。白天在待辦卡片上標「準備開工」，就算排進今晚。
2. 下班前做一個動作「下班派工」：開一個夜班批次，依並行上限跑完今晚所有準備開工的卡。
3. 夜班的卡用 work-mode 做，brief 只覆寫夜裡做不到的事：不等確認、不問問題、開 Draft PR 後回報狀態就結束。
4. 卡片結束回合但沒有回報，或卡在權限確認時，VibeFlow 把它標成「待你確認」並讓出名額。
5. 夜班一直開著、持續補位，直到早上按「停止派工」才結束並產生晨報。晨報把需要人處理的卡排在最前面。
6. 隔天方向錯的卡，可以寫下修正方向後重新標「準備開工」，下次派工時用新 session 在同一個分支接續。

## 已定案決策

- 移除盤點欄、headless 盤點 pass、盤點面板、`task inventory` 指令、`inventoryCommands` 設定，以及「盤點中」「待回答」兩個狀態標籤。
- 「今晚的清單」就是所有帶「準備開工」的卡：先待辦，再進行中的重派卡，各自依欄內順序。
- 並行上限沿用設定 `autonomous.concurrency`（預設 2），名額規則和 autonomous-run 相同。額度不夠時由既有的 heartbeat 等待重置再接續。
- 晨報在人按「停止派工」時產生。批次裡的卡全部停下來也不會自動收批（一張卡被誤判停下，就會讓整晚提早收工）；不提供固定時間產生。
- 白天整理不強制走 master 卡。單張卡可以直接在待辦標準備開工。master 規劃時可以把子卡標成準備開工，留待下班派工。
- 派工不強制開 auto mode，沿用卡片或設定的 auto mode。晚上卡在權限確認，就由目標 4 的規則處理。
- 卡片不分類型。任務是 bug fix 還是 feature，由 work-mode 讀了需求來源後判斷；eBug 卡的描述列單號即可，work-mode 的第一步「讀需求來源」會去讀單。
- 夜班的 spec／plan 確認視為使用者預先授權，確認紀錄寫明「夜班預先授權，早上驗收」。推到共用分支、force push、secret、lock 檔仍然不在授權內。
- 相依（`after`）還沒全部完成的卡不會被派出，留在原處，晨報會列出。

## 範圍

### 本次包含

- 移除盤點：看板欄位、core 的盤點流程與 handler、CLI、Web UI、TUI、設定、兩個狀態標籤。
- store 升到 v6 的 migration：盤點欄的卡搬回待辦，保留使用者補充的 context，清掉兩個狀態標籤。
- 「排進今晚」：在待辦卡片上標記或取消「準備開工」。
- 下班派工：handler、CLI、看板 header 上的按鈕，以及批次進行中的顯示。
- 夜班 brief：交給 work-mode，加上夜班覆寫規則與回報狀態的指令。
- 夜班卡片停下來時的偵測：結束回合但沒有回報、卡在權限確認。
- 按「停止派工」結束夜班並產生晨報；晨報排序與標題調整。
- 重派：進行中的卡帶著修正方向重新標「準備開工」，下次派工時換新 session 接續。
- master 的系統提示補上「今晚派工」的做法；`task create --ready`。
- 文件與測試。

### 本次不包含

- 固定時間派工或產生晨報。
- 早上驗收的專用畫面（Ready、merge 仍在 GitHub 上操作）。
- TUI 的派工操作。
- 修改 work-mode 本身。夜班的覆寫規則寫在 brief 裡，work-mode 不需要知道夜班。
- Codex 的額度偵測（autonomous-run 記載的已知限制）。

## 行為

### 白天：排進今晚

| 情境 | 預期行為 |
| --- | --- |
| 在待辦卡片的選單按「排進今晚」 | 卡片掛上「準備開工」。再按一次取消。卡片留在待辦，不建立 worktree。 |
| `task create --ready` 或 `task status --set ready` | 和上一列相同。 |
| 看板 header | 沒有夜班時，顯示「下班派工（N）」按鈕，N 是今晚可以派出的卡數；N 為 0 時按鈕停用。 |
| `task status --set inventorying` 或 `needs_answer` | 失敗，列出可用的狀態（這兩個狀態已移除）。 |
| `task create --status inventory`、`task inventory …` | 失敗：未知的欄位或指令。 |

### 下班派工

| 情境 | 預期行為 |
| --- | --- |
| 按「下班派工」或執行 `vibeflow dispatch` | 開一個夜班批次，依今晚清單的順序派出卡片，直到並行上限。派出的卡掛「執行中」。 |
| 沒有任何可派出的卡 | 拒絕，錯誤碼 `NOTHING_READY`，不開批次。 |
| 已經有夜班在進行 | 不再開新批次，只觸發一次補位。 |
| 夜班進行中，有卡片讓出名額 | 補派下一張。夜班開始後才標準備開工的卡也會被補派。 |
| 派出待辦的卡 | 照 `startTask` 的流程建立分支與 worktree 並啟動。失敗時卡片退回待辦並掛「卡住」，原因寫在狀態上，記進批次。 |
| 派出重派的卡（進行中且帶準備開工） | 換新 session（沿用 `continueTask`），brief 先放狀態原因裡寫的修正方向。 |
| 相依還沒完成的卡 | 不派出，也不算可派出的卡。 |
| 按「停止派工」或執行 `vibeflow dispatch --stop` | 不再補派，執行中的卡繼續跑完，批次結束並產生晨報。 |

### 夜班執行

| 情境 | 預期行為 |
| --- | --- |
| 派出的卡第一次啟動 | 第一則訊息是夜班 brief：卡片內容、「用 work-mode 處理」、夜班覆寫規則、回報狀態的指令。 |
| work-mode 要等 spec／plan 確認 | 不等。確認視為預先授權，確認紀錄寫「夜班預先授權，早上驗收」，接著往下做。 |
| work-mode 會停下來問的情況 | 不問。兩種解讀都說得通時選比較保守的，把假設寫進 PR 內文。 |
| work-mode 開出 PR 後 | 一律 Draft。回報「已開 PR」並附連結，然後結束這一回合，不盯 PR。 |
| 無法繼續 | 「卡住」或「待你確認」加上原因，然後停止。 |
| 派出的卡結束回合，但狀態仍是「執行中」或沒有狀態 | VibeFlow 改掛「待你確認」，原因是「agent 結束回合但沒有回報狀態」，名額讓出。 |
| 派出的卡結束回合，但它開的背景任務（背景指令、async sub-agent）還沒回報結束 | 不改狀態：agent 是在等自己的背景任務，收到 task-notification 會自己繼續。 |
| 派出的卡卡在權限確認 | VibeFlow 改掛「待你確認」，原因是「卡在權限確認」，名額讓出。 |
| 碰到額度上限 | 沿用 autonomous-run：等待重置，然後接續原 session。 |
| 卡片不是派出的（手動拖進進行中） | 照原本的方式啟動，不送夜班 brief；身上的「準備開工」會被清掉。 |

### 晨報

| 情境 | 預期行為 |
| --- | --- |
| 批次裡所有卡都停下來（已開 PR、卡住、待你確認、已完成或被刪除），而且沒有可補派的卡 | 夜班維持開著，之後標成準備開工的卡照樣補派。按「停止派工」才結束批次並產生晨報。 |
| 晨報的內容 | 標題「晨報」加日期。先列「需要你處理」（卡住、待你確認、仍在進行中），再列「等你驗收」（已開 PR）。格式沿用 autonomous-run 的表格加敘述。 |
| 今晚清單裡沒被派出的卡（例如相依未完成） | 晨報另列一段「沒有派出」。 |
| 舊批次的事件裡有已移除的狀態 | 照原本的名稱顯示（盤點中、待回答），不會出錯。 |

### 隔天：重派

| 情境 | 預期行為 |
| --- | --- |
| 進行中的卡方向錯了 | 在卡片選單按「改方向重派…」，寫下修正方向。卡片掛「準備開工」，原因就是修正方向。 |
| 下次派工 | 這張卡換新 session，在同一個分支接續，修正方向放在 brief 最前面。 |

### 舊資料（store v5 → v6）

| 情境 | 預期行為 |
| --- | --- |
| 盤點欄有卡 | 搬到待辦最前面，保持原本順序。worktree、分支都保留。 |
| 這些卡的狀態 | 「準備開工」保留，今晚照樣能派；「盤點中」「待回答」清掉；在等盤點額度的，清掉等待紀錄與「等待額度」。 |
| 使用者在盤點區補充過的 context | 附加到卡片描述最後（「## 盤點時的補充」），不會遺失。 |
| 盤點寫過的 spec.md／plan.md | 留在 worktree 裡，work-mode 繼續同一個功能時會沿用既有文件。 |
| 標籤清單裡的「盤點中」「待回答」 | 移除。 |
| 舊版程式讀到 v6 store | 讀成盤點欄是空的，不會壞。 |

### 白天：派工準備（night-prep skill）

| 情境 | 預期行為 |
| --- | --- |
| 使用者說要今晚派工、下班派工、準備派工（master 卡或一般 session 都可以） | agent 用 `night-prep`：重述要做的事，依 work-mode 的分類判斷每一項是什麼類型。 |
| 判斷出類型後 | 依該類型的 playbook 盤點：bug fix 要能重現的資訊、feature 要驗收條件與已定案的設計、refactor 要有保護行為的測試、補測試要範圍與慣例、依賴變更要先取得 lock 檔同意、調查要問題與產出形式。 |
| 不適合夜班的項目（設計未定、重現不了、處理既有 PR、lock 檔未同意） | 不建卡，或先拆出白天能完成的前置卡；回報裡寫明原因。 |
| 拆卡 | 一晚做得完、早上審得完；不同卡不改同一個檔案；有先後用 `--after`。 |
| 資源檢查 | 從專案的 AGENTS.md／CLAUDE.md 與套件設定找出安裝、測試、registry、`gh` 的指令實際執行，只記錄通過或失敗，不讀出 secret 的值。缺的列給使用者，補好後再檢查。 |
| 回報 | 寫 plan.md（拆卡、每張卡的任務單、檢查結果），停下來等使用者確認。 |
| 使用者確認後 | 用 `task create --ready` 建卡（有先後加 `--after`），不 `task start`。每張任務單自包含：背景、範圍、驗收條件、白天已定案的決定、資源檢查指令。 |
| 板子是唯讀（沒有 `VIBEFLOW_CLI`） | 把任務單整理好交給使用者手動建卡。 |
| 夜班開工 | 任務單有「資源檢查」時，第一步先重跑；有失敗就標「卡住」並寫明缺什麼，不往下做。 |

## 限制與依賴

- 結束回合和卡在權限的判斷來自 `progress.ts` 的 activity。Codex 沒有權限對話框的訊號，所以 Codex 只會偵測到結束回合。
- work-mode 是 VibeFlow 內建 skill，經由 Library 送進每張卡。使用者在 Library 停用 work-mode 時，brief 仍然要求用它，agent 會找不到；這時 agent 照 brief 的覆寫規則自行處理。
- 夜班 brief 裡的授權範圍遵守全域規則：推到共用分支、force push、secret、lock 檔都不能事先授權，只能列為停止條件。
- eBug 卡要靠使用者本機的 eCL MCP 讀單；讀不到就掛「卡住」。
