# Spec：日夜接力（下班派工與晨報）

- 狀態：已確認
- Ticket：尚無
- 需求來源：使用者的「日夜接力開發流程」設計圖（2026-11-26）。人在白天決定要做什麼，下班前派工；AI 趁夜做完，每張卡開一個 Draft PR；隔天早上先看總表，再逐張驗收、當天收尾。
- 更新日期：2026-11-26
- 確認紀錄：2026-11-26 使用者看過改版方向後回覆「可以，寫完規格與計畫就開始實作」。其中三個待決定事項（並行上限、晨報時間、是否一定要走 master）沒有另外回答，依建議預設定案，見「已定案決策」。
- 取代：[autonomous-run](../autonomous-run/spec.md) 的「放行開關」與「關閉時產生報告」；其餘部分（狀態標籤、額度等待、批次事件、報告格式）沿用。

## 問題與目標

[autonomous-run](../autonomous-run/spec.md) 的設計是持續排隊、逐步消化，跟實際的工作節奏對不上：

- **盤點是每張卡各跑一輪 headless pass。** 有問題要等 pass 結束、補 context、再跑一輪，人不能直接和 AI 對話。盤點也不會拆卡或合卡，但白天最需要的就是把 Feature 拆小、把同元件的 eBug 合併。
- **放行是一個開關。** 要記得打開，也要記得關掉，關掉才產生報告。實際需要的只是「下班時按一次」。
- **晚上只有一種做法。** Feature 和 eBug 晚上要做的事不同：eBug 要照單重現、量測、修正後再量一次，再附截圖。
- **agent 結束回合但沒有回報時，卡片會一直佔著名額。** 晚上沒人守著，這張卡會卡住整個批次，報告永遠出不來。
- **方向錯的卡沒有「改單、當晚重派」的路徑。**

目標：

1. 白天在 Backlog 或盤點欄把卡片標成「準備開工」，就算排進今晚。不一定要經過盤點。
2. 下班前做一個動作「下班派工」：開一個夜班批次，依並行上限跑完今晚所有準備開工的卡。
3. 晚上依卡片類型（Feature／eBug）給不同的做法，一律開 Draft PR，用狀態標籤回報結果。
4. 卡片結束回合但沒有回報，或卡在權限確認時，VibeFlow 把它標成「待你確認」並讓出名額。
5. 批次裡的卡片都停下來後，夜班自動結束並產生晨報。晨報把需要人處理的卡排在最前面。
6. 隔天方向錯的卡，可以寫下修正方向後重新標「準備開工」，下次派工時用新 session 在同一個分支接續。

## 已定案決策

- 盤點欄保留，但不再是必經的一關，改成白天選用的工具，用在「原因不明，先請 AI 查」。欄位 id 不變，不需要搬移資料。
- 「今晚的清單」就是所有帶「準備開工」的卡：先盤點欄，再待辦，各自依欄內順序；進行中的重派卡排在最後。
- 並行上限沿用設定 `autonomous.concurrency`（預設 2），名額規則和 autonomous-run 相同。額度不夠時由既有的 heartbeat 等待重置再接續。
- 晨報在批次裡的卡全部停下來時自動產生。不提供固定時間產生。
- 白天整理不強制走 master 卡。單張卡可以直接在 Backlog 標準備開工。master 規劃時可以把子卡標成準備開工，留待下班派工。
- 派工不強制開 auto mode，沿用卡片或設定的 auto mode。晚上卡在權限確認，就由第 4 點的規則處理。
- 卡片類型只有兩種：`feature`（預設）與 `ebug`。舊卡片沒有這個欄位，一律視為 feature。
- 相依（`after`）還沒全部完成的卡不會被派出，留在原處，晨報會列出。

## 範圍

### 本次包含

- 卡片類型 `kind`：新卡片對話框、編輯對話框、`task create --kind`、卡片上的類型標示。
- 「排進今晚」：在 Backlog 卡片上標記或取消「準備開工」。
- 下班派工：handler、CLI、看板 header 上的按鈕，以及批次進行中的顯示。
- 夜班執行提示：依類型產生第一則訊息，盤點過的卡也套用。
- 夜班卡片停下來時的偵測：結束回合但沒有回報、卡在權限確認。
- 夜班自動結束並產生晨報；晨報排序與標題調整。
- 重派：進行中的卡帶著修正方向重新標「準備開工」，下次派工時換新 session 接續。
- master 的系統提示補上「今晚派工」的做法；`task create --ready`。
- 文件與測試。

### 本次不包含

- 改名或移除盤點欄（欄位 id 和 migration 都不動）。
- 固定時間派工或產生晨報。
- 早上驗收的專用畫面（Ready、merge 仍在 GitHub 上操作）。
- TUI 的派工操作。TUI 只顯示卡片類型。
- Codex 的額度偵測（autonomous-run 記載的已知限制，不在本次範圍）。

## 行為

### 白天：排進今晚

| 情境 | 預期行為 |
| --- | --- |
| 建立卡片時選類型 | 對話框有「類型」選項：Feature／eBug，預設 Feature。CLI 用 `--kind feature\|ebug`。master 卡沒有類型。 |
| eBug 卡片的描述 | 列出 eBug 單號即可，晚上由 agent 自己讀單。對話框的描述欄提示這一點。 |
| 在 Backlog 卡片上按「排進今晚」 | 卡片掛上「準備開工」。再按一次取消。卡片留在 Backlog，不建立 worktree。 |
| `task create --ready` 或 `task status --set ready` | 和上一列相同。 |
| 盤點完成的卡 | 和現在一樣掛「準備開工」，也算在今晚的清單裡。 |
| 看板 header | 沒有夜班時，顯示「下班派工（N）」按鈕，N 是今晚可以派出的卡數；N 為 0 時按鈕停用。 |

### 下班派工

| 情境 | 預期行為 |
| --- | --- |
| 按「下班派工」或執行 `vibeflow dispatch` | 開一個夜班批次，依今晚清單的順序派出卡片，直到並行上限。派出的卡掛「執行中」。 |
| 沒有任何可派出的卡 | 拒絕，錯誤碼 `NOTHING_READY`，不開批次。 |
| 已經有夜班在進行 | 不再開新批次，只觸發一次補位。 |
| 夜班進行中，有卡片讓出名額 | 補派下一張。白天之後才標準備開工的卡也會被補派。 |
| 派出待辦的卡 | 照 `startTask` 的流程建立分支與 worktree 並啟動。失敗時卡片退回待辦並掛「卡住」，原因寫在狀態上，記進批次。 |
| 派出重派的卡（進行中且帶準備開工） | 換新 session（沿用 `continueTask`），brief 加上狀態原因裡寫的修正方向。 |
| 相依還沒完成的卡 | 不派出，也不算可派出的卡。 |
| 按「停止派工」或執行 `vibeflow dispatch --stop` | 不再補派，執行中的卡繼續跑完，批次結束並產生晨報。 |

### 夜班執行

| 情境 | 預期行為 |
| --- | --- |
| 派出的卡第一次啟動 | 第一則訊息是夜班 brief：卡片內容、「沒有人在線上，不要停下來問問題」、依類型的步驟、回報狀態的指令。盤點過的卡另外指向它的 spec 和 plan。 |
| Feature 的步驟 | 做法不確定時先寫 plan，再實作、補 unit test，做 AI 自我 review，lint／typecheck／test 全部通過後開 Draft PR，plan 附在 PR 內文。 |
| eBug 的步驟 | 讀單（用 `ebug` skill 或 eCL），照單重現並量測，修正後再量一次，截圖存進 Artifacts，也附進 PR；同一張卡的多張單一起處理。之後的自我 review、檢查、Draft PR 和 Feature 相同。 |
| 開出 Draft PR | agent 把狀態設為「已開 PR」，原因寫 PR 連結。 |
| 無法繼續 | 「卡住」或「待你確認」加上原因，然後停止。 |
| 派出的卡結束回合，但狀態仍是「執行中」或沒有狀態 | VibeFlow 改掛「待你確認」，原因是「agent 結束回合但沒有回報狀態」，名額讓出。 |
| 派出的卡卡在權限確認 | VibeFlow 改掛「待你確認」，原因是「卡在權限確認」，名額讓出。 |
| 碰到額度上限 | 沿用 autonomous-run：等待重置，然後接續原 session。 |

### 晨報

| 情境 | 預期行為 |
| --- | --- |
| 批次裡所有卡都停下來（已開 PR、卡住、待你確認、已完成或被刪除），而且沒有可補派的卡 | 批次自動結束並產生晨報，派工按鈕恢復可用。 |
| 晨報的內容 | 標題「晨報」加日期。先列「需要你處理」（卡住、待你確認、仍在進行中），再列「等你驗收」（已開 PR）。格式沿用 autonomous-run 的表格加敘述。 |
| 今晚清單裡沒被派出的卡（例如相依未完成） | 晨報另列一段「沒有派出」。 |

### 隔天：重派

| 情境 | 預期行為 |
| --- | --- |
| 進行中的卡方向錯了 | 在卡片上按「改方向重派」，寫下修正方向。卡片掛「準備開工」，原因就是修正方向。 |
| 下次派工 | 這張卡換新 session，在同一個分支接續，修正方向放在 brief 最前面。 |
| 小問題直接修 | 不需要新功能，照現在的方式在終端機裡處理。 |

## 驗收條件

- [ ] AC-1：建立 eBug 類型的卡片（UI 和 CLI 都可以），卡片存有 `kind: 'ebug'`，看板上看得到類型。
- [ ] AC-2：Backlog 卡片按「排進今晚」後掛上「準備開工」，再按一次取消；不會建立 worktree。
- [ ] AC-3：並行上限為 2，Backlog 有 3 張準備開工的卡，下班派工後前 2 張進入進行中並各自啟動，掛「執行中」；其中一張改成「已開 PR」後，第 3 張被補派。
- [ ] AC-4：沒有準備開工的卡時，派工失敗並回傳 `NOTHING_READY`。
- [ ] AC-5：派出的 Feature 卡和 eBug 卡，第一則訊息分別包含各自的步驟，而且都要求開 Draft PR 和回報狀態。
- [ ] AC-6：派出的卡結束回合但沒有回報狀態時，被改成「待你確認」並讓出名額。
- [ ] AC-7：批次裡的卡全部停下來後，批次自動結束，晨報出現在報告列表；需要處理的卡排在已開 PR 的卡前面。
- [ ] AC-8：進行中的卡標「準備開工」並寫下修正方向，下次派工時換了新 session（`runId` 改變），brief 包含修正方向。
- [ ] AC-9：相依未完成的準備開工卡不會被派出，晨報列在「沒有派出」。
- [ ] AC-10：舊的 `vibeflow-state.json`（沒有 `kind`、`dispatch`）讀入後行為不變；`release on/off` 和盤點仍可使用。

## 限制與依賴

- 結束回合和卡在權限的判斷來自 `progress.ts` 的 activity。Codex 沒有權限對話框的訊號，所以 Codex 只會偵測到結束回合。
- 新增的卡片欄位 `kind`、`dispatch` 都是選填，舊資料讀入時視為沒有，所以不升 `STATE_VERSION`，也不需要 migration。
- 夜班 brief 裡的授權範圍遵守全域規則：推到共用分支、force push、secret、lock 檔都不能事先授權，只能列為停止條件。
- 晚上 agent 能不能用 `ebug` skill 讀單，取決於使用者本機的 MCP 設定；讀不到就掛「卡住」。
